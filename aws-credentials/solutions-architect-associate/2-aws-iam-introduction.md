# 1. Identity Access Management [`IAM`]

IAM은 Identity Access Management의 약자로 AWS 리소스에 대한 계층화된 권한을 관리하고 전반적인 액세스를 제어할 수 있는 서비스이다. 리소스를 사용하도록 인증 2FA, SAML SSO, TOTP 등 다양한 인증과 권한 부여 대상을 제어한다. 이는 인증 및 권한 부여를 제어하는 데 필요한 인프라를 제공한다.

#### ID

* AWS 계정을 생성하는 시점부터 모든 AWS 서비스와 리소스에 대한 액세스 권한이 있는 AWS 계정 루트 사용자의 단일 로그인 ID로 시작한다. 루트 사용자를 사용하지 않는 것을 원칙으로 하여 루트 사용자 자격 증명이 필요한 작업은 별도로 다른 ID로 설정하고 수행하는 데 필요한 리소스에 대한 액세스 권한을 제어할 수 있다.

#### 액세스 관리 [`Access Manage`]

* IAM에 설정된 사용자는 로그인 자격 증명을 사용하여 AWS에 인증하기 때문에 AWS 계정에서 신뢰하는 위탁자와 로그인 보안 인증 정보를 일치시키는 방식으로 인증이 제공된다. `위탁자`에게 리소스 액세스 권한을 부여하도록 요청이 이루어져 리소스에 대한 권한이 부여된 경우 권한 부여 요청에 대한 응답으로 액세스 권한이 부여된다.

* 서비스를 선택하면 인증 요청이 해당 서비스로 전송되어 인증된 사용자 목록에 ID가 포함되어 있는지 부여된 액세스 수준을 제어하기 위해 어떤 정책이 적용되고 있는지 확인한다. AWS 계정 내의 `위탁자`나 신뢰할 수 있는 AWS 계정을 통하여 인증을 요청할 수 있다.

> [!NOTE]
> * **위탁자**
>   * IAM 사용자
>   * AWS STS 페더레이션 위탁자
>   * IAM 역할 또는 애플리케이션

## 1.1 서비스 가용성

* IAM은 많은 AWS 서비스처럼 최종 일관성을 유지하며 데이터 센터 내의 여러 서버로 데이터를 복제함으로써 고가용성을 추구한다.
* 일부 데이터를 변경 요청이 성공하면 변경이 진행된 후 저장되고 변경 사항은 IAM 전체에 복제되어야 하고 이는 일정 시간 이상의 소요가 발생한다.
* 변경 사항에는 사용자, 그룹, 역할 또는 정책을 만들거나 업데이트한 것이 포함되어 변경 사항을 애플리케이션의 중요한 고가용성 코드 경로에 포함시키지 않는 것을 권장한다.
* 비활성화 상태의 초기화 루틴이나 설정 루틴에서 IAM을 변경하고 프로덕션 워크플로우에서 변경 사항을 적용하기 전에 변경 사항이 배포되었는지 확인해야한다.

### 1.1.1 서비스 비용 정보 [`Service Cost Information`]

* `AWS Identity and Access Mangement`, `AWS IAM Identity Center`, `AWS Securty Token Service`는 추가 비용 없이 제공되는 기능이다. 
* IAM 사용자 또는 AWS STS 임시 보안 자격 증명을 사용하여 다른 AWS 서비스에 액세스하는 경우에만 요금이 부과된다.
* `IAM Access Analyzer` 외부 액세스 분석은 추가 비용 없이 제공되만, 비활성화 액세스 분석 및 고객 정책 확인에는 요금이 발생한다.

> [!NOTE]
> * **AWS Security Token Service (`AWS STS`)**
> * **AWS IAM Identity Center**
>   * AWS 애플리케이션에 대한 인력 액세스 관리에 권장되는 서비스이다. 기존 ID 소스를 한 번 연결하여 사용자들에게 AWS 애플리케이션에 대해 공통된 관점을 제공하는 데 사용할 수 있는 솔루션이다.
>   * 사용자들은 AWS 애플리케이션 전반에서 간소화되고 일관된 경험을 할 수 있으며, 기존 AWS 계정 액세스 구성과 함께 작동한다.
> * **IAM Access Analyzer**
>   * 최소 권한은 요구 사항의 변화에 따라 적절하게 세분화된 권한을 부여하여 지속적인 목표를 달성할 수 있다.
>   * 권한을 설정, 확인, 조정할 수 있는 기능을 제공하여 최소 권한을 사용하도록 안내한다.

# 2. IAM 접근 권한 타입 [`IAM Access Authority Type`]

* IAM은 AWS 신원 및 접근 관리는 권한을 안전하게 관리할 수 있게 해주는 도구이다. AWS 리소스 IAM 사용의 주요 장점 중 하나인 하나는 공유 할당이 가능하기 때문에, 계정에 대한 접근 권한 또한 세세한 권한을 할당하여 미래의 사용자가 어떤 행동을 다룰지 정확히 제어할 수 있는 부분이다.
* 사용자는 특정 자원에서 공연할 수 있으며 이러한 수준의 접근 통제는 매우 중요하기 때문에 AWS 환경의 고수준 보안을 유지하는 것이 목표이며 여러 보안 기능을 제공한다.

> [!NOTE]
> * **다중 인증 (MFA)**
>   * Virtual MFA Device
>   * Universal 2nd Factor Security Key
>   * Hardware Key Fob MFA Device
>   * Hardware Key Fob MFA Device for AWS GovCloud (US)
> * Identity 페더레이션 신원 제공자
> * AWS CloudTrail

## 2.1 AWS 계정에 대한 공유 접근 권한 특징

#### 세분화된 권한

서로 다른 자원에 대해 다른 사람에게 권한을 부여할 수 있다. 일부 사용자에게 `Elastic Cloud Computing`, `Simple Storage Service`,`S3`, `DynamoDB`, `Reshift` 및 기타 AWS 서비스에 대한 완전한 접근 권한을 허용할 수 있으며 추가로 별도의 사용자에게 특정 부분만 허용하거나 모든 권한을 부여할 수 있지만 S3 버킷에 대한 읽기 전용 접근이나 관리 권한 EC2 인스턴스에 청구 접근만 가능하지만 이후 어떠한 행동을 취할 수는 없다.

#### 애플리케이션에 대한 AWS 리소스 보안 접근

IAM 기능을 사용해 실행되는 애플리케이션에 대해 안전하게 자격 증명을 제공할 수 있고, EC2 인스턴스에서 사용된다. 이 자격 증명들은 애플리케이션이 접근할 수 있도록 기타 AWS 접근에 대한 권한을 부여한다.

#### 다중 인증 [MFA]

계정에 2단계 인증을 추가와 개별 사용자에게도 별도의 추가 인증 수단을 적용할 수 있다. MFA에서는 사용자들이 비밀번호나 접근 권한만 제공하는 것이 아니라 계정과 함께 작동할 수 있는 키와 함께 특별히 설정된 기기에서 나오는 일련번호 형태의 코드도 필요하다. 기존에 다른 서비스와 `FIDO` 보안 키를 사용하고 있고 AWS 포함하여 지원하여 구성에 대해 WebAuthn을 MFA 보안을 사용할 수 있다.

#### 정체성 연합

이미 다른 곳에서 비밀번호를 가지고 있는 사용자를 허용할 수 잇으며, 접근권한 AWS 계정과 IAM 기준에 가장 적합한 임시 자격 증명을 부여하여 신원 연합을 사용하면 AWS의 보안을 강화할 수 있다.

#### 보증을 위한 신원 정보

사용자의 자원 요청에 관한 정보를 포함한 기록 계좌 로그를 받고 IAM 신원을 기반으로 한다.

## 2.2 PCI DSS 준수

IAM은 처리, 저장, 전송을 지원해 서비스 제공자에 의해 신용카드 데이터에 대한 정보와 결제 산업(PCI) 데이터 보안 표준(DSS)을 준수하는 것으로 검증되었다.

# 3. IAM은 언제 사용하는 것이 적합한가?

* IAM의 신원 및 접근 관리는 출입 제어의 기반을 제공하는 핵심 인프라 서비스이다. AWS내 신원을 기반으로 하여 계정에 접근 시도할 때마다 IAM을 사용하기 때문에 어떻게 사용하느냐에 따라 구체적인 책임과 업무 기능이 달라진다. 
* IAM통해 AWS 리소스에 접근하여 관리자가 적절한 권한을 부여하는 업무를 진행하며 역할과 상관없이 인증할 때마다 상호작용하게 되면서 AWS 리소스에 대한 접근 권한을 부여한다. 이는 사용자로 로그인 하는 것도 포함된다.
* 정책과 권한 생성에 있어 유연하고 세밀한 접근법을 요구하며 어떤 주체가 할 수 있는지 통제할 수있도록 신뢰 정책을 정의할 수 있다.
* 행동과 장원을 명시하는 식별 기반 정책 외에 역할 수행하고 이러한 IAM 정책을 설정함으로써 사용자가 그리고 애플리케이션은 필요한 작업을 수행할 수 잇는 적절한 권한 수준을 가지고 있다.

## 3.1 다양한 업무를 수행

IAM 사용 방식은 AWS에서 하는 작업에 따라 다르다.
* **서비스 사용자**
  * AWS 서비스를 사용해 업무를 수행한다면, 관리자가 적절한 자격 증명과 권한을 제공한다. 확장된 업무를 수행을 하고자 하면 추가 권한이 필요할 수 있으며 접근성 관리는 관리자에게 올바른 권한을 요청하는데 도움을 줄 수 있다.
* **서비스 관리자**
  * 회사에서 AWS 리소스를 담당하고 있다면, IAM에서 완전히 접근할 수 있지만 IAM에서 어떤 권한을 부여해야 서비스 이용자가 접근할 수 있는지에 대한 요청을 제출해야 한다. 관리자가 서비스 사용자의 권한을 변경할 수 있고 정보를 바탕으로 검토해야 한다.
* **IAM 관리자**
  * IAM 접근 관리 위한 정책을 작성하고 신원을 관리한다.

#### AWS 리소스에 접근할 권한이 부여

* 인증은 신원 증명을 사용해 AWS에 로그인하는 방법으로 AWS 계정 루트 사용, IAM 사용자 또는 IAM 역할을 수행하여 인증 받아야한다.
* `AWS IAM Identity Center`, `Single Sign-On (SSO)`, `Flatform Credential` 등 신원 소스 출처의 자격 증명을 통해 연합 신원으로 로그인할 수 있다.
* 프로그래밍 접근을 위해 AWS는 요청을 암호화 서명할 수 있는 SDK와 CLI를 제공한다.

#### IAM 사용자로 로그인

IAM 사용자는 특정 개인이나 애플리케이션에 대한 특정 권한을 가진 신원이다. 장기 인증 정보를 가진 IAM 사용자 대신 임시 자격 증명(`페더레이션`)을 사용하는 것을 AWS에서는 적극 권장한다.

#### IAM 역할 이행

IAM 역할은 임시 자격 증명을 제공하는 특정 권한을 가진 신원이며, 사용자는 사용자에서 IAM 역할으로 전환하거나 SDK 통해 API를 호출하거나 CLI로 역할을 수행할 수 있다.

#### 정책과 권한을 생성

사용자에게 권한을 부여하려면 정책을 생성하는데 이 정책은 사용자가 수행할 수 있는 범위와 행동에 대한 영향을 미칠 수 있는 자원이다. 어떤 행동이나 명시적으로 허용되지 않은 자원은 기본적으로 요청이 거부되며 정책은 생성될 수 있으며 별도의 주체에 적용할 수 있다.

**IAM 역할과 함께 다음 정책을 사용할 수 있다.**
* **신탁 정책**
  * 어떤 소유자가 조건에서 역할을 맡을 수 있는지 정의하고, 신탁 정책은 IAM 역할에 대한 특정 유형의 리소스 기반 정책이나 역할은 단 하나의 신뢰만 가질 수 있다.
* **신원 기반 정책 (`인라인 및 관리형 정책`)**
  * 역할 사용자가 수행할 수 있는 권한을 정의한다.

IAM Identity Center를 사용해 사용자를 관리중이면, 권한 정책을 첨부하는 대신 권한 세트를 할당하면 된다. 그룹 또는 사용자에게 권한 세트를 할당하면 IAM Identity Center에서 생성하고 각 계정 내 대응하는 역할을 부여해 다음 계정에 명시된 정책을 첨부한다. 그 역할들에 권한이 설정되어 IAM Identity Center에서 역할을 관리해 권한 집합을 수정하면 IAM Identity Center는 해당 IAM 정책과 역할도 이에 따라 업데이트된다.

계정 접근 관리자(Acount Access Manger)를 사용하여 기존 IAM 역할을 생성하고 관리해 IAM Identity Center 사용자와 그룹에 할당하여 전체 IAM 역할 기능을 사용할 수 있게 한다. 별도로 권한 세트와 함께 사용하거나 단독으로 사용할 수 있다.

# 4. IAM 관리의 중요성

AWS 환경에서 신원 및 접근 관리를 활용하려면 다양한 도구들을 통해 효율성을 높일 수 있다. 일반적인 방법으로 인터페이스 형식인 AWS Management Console의 웹 기반 인터페이스를 통하고 사용자 생성 부터 다양한 IAM 관리 작업을 수행할 수 있게 해주며 권한 설정에 대한 역할 등이 존재한다.

명령줄 인터페이스(`Command Line Interface`)에 익숙한 사용자는 AWS에서 제공하는 두 가지 세트의 명령줄 도구와 `명령줄 인터페이스`외 `Windows PowerShell`용 AWS 도구을 제공한다. IAM 관련 발급을 진행하면서 터미널에서 직접적인 명령이 이루어져 콘솔을 통해 탐색하는 것보다 외부적인 요소에서 효율적으로 나타난다. 또한 AWS CloudShell은 웹에서 CLI 또는 SDK 명령을 직접 실행할 수 있도록 해준다.

Console 과 CLI 외에도 소프트웨어 개발 키드(`Software Develop Kit`)를 제공하기 때문에 다양한 프로그래밍 언어를 통하여 IAM 관리 기능을 통합할 수 있기 때문에, 프로그래밍적으로 IAM에 접근할 수도 있으며 IAM 쿼리 API는 서비스에 직접 HTTPS 요청을 보낼 수 있다. 이는 다양한 관리 방식을 활용하여 유연성을 갖추게 되고 기존 워크플로우와 프로세스에 IAM을 통합할 수 있다.

## 4.1 AWS Console Manage

AWS 관리 콘솔은 광범위한 분야를 포함하고 참조하는 웹 애플리케이션이다. AWS 자원을 관리하기 위한 서비스 콘솔 모음, 최초 로그인에 대한 홈페이지를 참조하고 각 서비스 콘솔에 대한 접근을 제공한다. 필요한 정보를 단일 장소에서 확인할 수 있으며 콘솔에 로그인 후 이용 가능한 서비스와 애플리케이션은 접근 권한이 있는 AWS 리소스에 따라 다르다.

역할을 맡거나 그룹의 일원이 되는 경우를 통해 자원에 대한 권한 허가를 받았거나 명시적으로 허가를 받은 경우, 독립적인 작품으로서 AWS 계정, 루트 사용자 또는 IAM 관리자가 리소스 접근 권한을 설정하여 AWS 조직, 관리 계정 또는 위임된 관리자가 다음 접근 권한을 구성한다.

AWS 관리 콘솔을 사용하는 사용자들이 AWS를 관리할 계획이 있다면 보안 모범 사례를 인용해 임시 자격 증명을 사용하는 사용자를 구성할 것을 권장한다. 역할을 부여된 IAM 사용자들, 연합된 주체와 IAM 신원 센터 내 사용자는 임시 자격 증명을 가져, IAM 사용자와 루트 사용자는 장기 자격 증명을 가지고 있기 때문에 자격 증명은 다음 AWS 계정과 다른 사용자들은 접근 권한을 제공하는 자격 증명을 가지어 IAM 정책에 의해 부여된 자원이다.

로그인의 사례 케이스는 AWS Management Console 사용자 유형은 다음과 같다.

* IAM 사용자와 루트 사용자 모두 AWS 로그인 URL에서 로그인하면 다음 계정에 접근할 수 있지만 모두 허가받은 계좌의 파생된 내부 자원이다. 루트 사용자로 로그인을 하려면 해당 루트 사용자 이메일 주소와 비밀번호가 있어야 하며 IAM 사용자로 로그인을 하려면 AWS 계정 번호 또는 별칭이 있어야 하기 때문에 IAM 사용자 이름과 IAM 사용자 비밀번호가 필요하다.
* IAM Identity Center 사용자는 고유한 AWS 접근 포털을 통해 로그인하며 조직은 로그인하면 어떤 계정이나 애플리케이션을 선택할 수 있다. 계정에 접근하기로 하면 어떤 권한 세트를 선택하는지 결정하며 관리 세션에 사용하고 싶어할 경우이다.
* OIDC 및 SAML 연합 주체는 외부 신원 제공자에서 관리되며, AWS 계정 로그인은 맞춤형 엔터프라이즈 액세스 포털을 사용한다. AWS 사용자가 사용할 수 있는 자원은 선택된 정책과 조직에 따라 달라진다.

## 4.2 AWS 명령줄 도구 [`Command Line Tool`]

AWS 명령줄 도구를 사용해 시스템의 명령에 따라 행동을 정할 수 있으며, IAM과 AWS 작업을 수행하는 라인을 사용한다. 명령줄 사용이 더 빠르고 콘솔보다 편리해 효과적일 수 있기에 AWS CLI와 AWS Windows PowerShell을 통하여 진행할 수 있다. 콘솔에 로그인 후 브라우저에서 AWS CloudShell을 사용해 CLI를 실행할 수 있으며 SDK, AWS Resource에 접근할 권한은 자격 증명 정책에 따라 결정된다.

## 4.3 AWS 명령줄 인터페이스 [`Command Line Interface`] and 소프트웨어 개발 키드 [`Software Develop Kit`]

IAM Identity Center와 IAM 사용자는 자격 증명을 인증하는 데 서로 다른 방법으로 사용하지만, 보통 CLI나 애플리케이션 인터페이스(`API`)를 통해 인증한다. IAM Identity Center와 IAM 모두 CLI 또는 SDK와 함께 사용할 수 있는 접근 키를 받고 IAM 신원 센터 접근 키는 자동으로 갱신할 수 있는 임시 자격 증명이지만 IAM 사용자와 관련된 장기 접근 키보다 우선적으로 권장한다.

CLI 또는 SDK를 사용해 AWS 계정을 관리하고자 하면 AWS CloudShell을 사용해 실행 전 로그인을 진행하고 콘솔에서는 AWS 리소스에 접근할 수 있는 권한의 조건인 자격 증명, 사례에 따라 상이하지만 대부분 CLI가 더 효율적인 관리 방법일 수 있다. 

애플리케이션 개발을 위해 CLI나 SDK를 로컬 컴퓨터에 다운로드하여 명령 프롬프트나 Docker 창에서 로그인하면 되고, CLI 스크립트나 SDK 애플리케이션의 일부로 인증 및 접근 자격 증명을 제공하기 때문에 자원에 대한 프로그래밍 접근을 다양한 방식으로 접근할 수 있어 환경과 이용 가능한 접근성이 용이하다.

> **AWS 액세스 포털을 통해 로그인할 경우 단기 자격 증명을 받을 수 있으며 시작 페이지에서 권한 세트를 선택할 수 있지만 이러한 자격 증명은 정의된 지속 시간과 자동으로 갱신되지 않기 때문에 AWS 계정에서 권한 설정을 선택후 명령줄 또는 프로그래밍 선택 AWS 리소스에 접근할 수 있는 옵션을 보고 프로그래밍적 명령이나 CLI에서 사용할 수 있다.**

## 4.4 IAM 쿼리 [`Query`] API

IAM 쿼리 API를 통해 프로그래밍적으로 IAM과 AWS에 접근할 수 있으며 서비스에 직접적인 HTTPS 요청을 보낼 수 있게 해주지만, 쿼리 API를 사용할 대 요청을 디지털 서명할 코드를 반드시 포함해야 한다.

# 5. IAM 프로세스 원리

<img width="50%" height="350" alt="image" src="https://docs.aws.amazon.com/images/IAM/latest/UserGuide/images/intro-diagram%20_policies_800.png" />

* IAM이 리소스에 대한 주요 접근 권한을 요청을 할 경우 승인 요청에 대한 응답으로 접근 거부를 할 수 있으며, 특정 서비스에 접근하는 것이 아닌 서비스를 선택 이후 접근 권한을 승인 요청을 하는 것이다.
* IAM 검증 신원이 권한 있는 사용자 목록에 포함된다면 어떤 정책이 이를 통제하는 것이지 결정하고 접근 권한이 부여된 수준을 평가해 시행 중인 다른 정책들도 평가한다.
* 승인이 이루어지면 소유자는 사용자의 자원에 대해 행동이나 작업을 수행할 수 있다.

## 5.1 요청의 구성 요소

프린시펄이 AWS 관리 콘솔, AWS API, 또는 AWS CLI를 사용하려 할 때 프린시펄은 AWS에 다음과 같은 요청서에 내용을 포함하여 보낸다.

* **행동 또는 연산**
  * 행동 또는 주체가 수행하고자 하는 작업들 또는 AWS 관리 콘솔에서의 동작이나 AWS CLI 또는 AWS API 내에서 동작하는 것도 포함된다.
* **리소스**
  * AWS 리소스 객체 주체가 어떤 동작이나 연산을 수행해 달라고 요청한다.
* **원칙**
  * 사람 또는 신청 요청을 보낼 엔티티를 사용했으며, 관련 정보 허가 정책 포함을 시킨다.
* **환경 데이터**
  * IP에 관한 정보 주소ㅗ, 사용자 에이전트, SSL 활성화 상태, 타임스탬프가 포함된다.
* **자원 데이터**
  * DynamoDB 테이블 이름이나 EC2 인스턴스와 같은 자원과 관련된 데이터를 요청한다.

## 5.2 주체에 대한 인증 방식

주체가 AWS에 로그인하는 작격증명을 사용하고, IAM이 이를 인증 허용을 하여 AWS에 요청을 보내도록 한다. 예를 들어 Amazon S3나 [AWS STS](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html)와 같은 일부 서비스는 이를 지원하고 익명의 사용자로 부터 구체적인 요청이 필요있기 때문에 예외적인 경우를 제외한 다음과 같은 해당하는 각 유형 사용자가 인증을 거친다.

* **연합 원금**
  * 사용자는 신원 제공자 인증을 받고 AWS에 자격을 전달해 주어지며, 직접적인 로그인이 필요하지는 않아 IAM Identity Center와 IAM 모두 신원 연합을 지원한다.
* **루트 사용자**
  * 로그인 자격 증명 인증에 사용되는 것은 AWS 계정을 생성할 대 사용한 이메일 주소와 당시 지정한 비밀번호가 포함된다.
* **IAM 사용자**
  * 계정 ID 또는 별명, 사용자 이름, 비밀번호의 API에서 워크로드를 인증하기 또는 AWS CLI를 사용해 임시 자격 증명을 사용할 수 있다.
* **AWS IAM Identity Center Directory**
  * IAM Identity Center 기본 디렉터리 서명에서 직접 생성된 사용자 aws 액세스 포털을 사용할 대 사용자 이름과 비밀번호를 제공해야 한다.

## 5.3 권한 부여 및 권한 정책 기본

권한이란 함은 주체가 작업을 완료할 수 있는 필요한 권한을 가진 것을 의미한다. 요청과 승인 과정에서 IAM은 요청에 적용되는 정책을 식별하고 요청 컨텍스트에서 값을들 얻는다. 이후 적용되는 정책에 대한 허용 여부를 결정하거나 거부할 수 있기에 IAM은 대부분의 구너한 정책은 JSON 문서로 저장하여 권한을 관리한다.

* Access Policy Role
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Service": "support.amazonaws.com"
            },
            "Action": "sts:AssumeRole"
        }
    ]
}
```

영향을 줄 수 있는 여러 유형의 정책이 존재하고 이에 따른 허가 요청이 필요하기 때문에 사용자에게 AWS 리소스에 접근할 권한을 부여하는 것으로 계정에서는 신원 기반 정책을 사용할 수 있다. 리소스 기반 정책은 계정 간 접근을 허용하여 요청하는 것을 다른 계정의 정책이 존재해야 하며 요청하는 데 사용하는 자원과 IAM Identity에 접근할 수 있어야 요청을 허용하는 신원 기반 정책이 무조건 필요하다.

IAM은 요청의 맥락에 적용되는 각 정책을 확인해 정책 평가에는 명시적 부정을 사용하고 이는 단일 권한 정책에는 거부된 동작이 포함되 전체 요청을 거부하고 중단한다. 요청이 기본적으로 거부 (`Reject`)되기 때문에 적용 가능한 권한 정책은 iam 요청의 모든 부분이 사용자의 권한을 부여할 수 있도록 다음과 같은 규칙을 준수하여 허용해야 한다.

* 기본적으로 모든 요청은 거부된다.
* 모든 권한 정책이 명시적 허용 이 기본값을 무시한다.
* AWS 조직의 서비스 제어 정책 (`SCP`) 또는 리소스 제어 정책의 존재 (`RCP`), IAM 권한 경계, 세션 정책이 허용을 덮는 경우 하나 이상의 경우 이러한 정책 유형 중 모두 요청을 허용해야 한다. 이런 절차를 하지 않은 경우 암묵적인 거부로 변경된다.
* 어떠한 정책이든 명시적 거부는 어떤 정책의 허용보다 우선한다.

IAM이 주체를 인증 후 승인을 한 후에 행동을 승인하거나 소유자에게 적용되는 권한 정책을 평가하고 요청 시 운영을 진행한다. 각 AWS 서비스는 지원하는 액션 (`Operation`)을 정의하며, 사용자들이 할 수 있는 것들도 포함된다.

* **CreateUser**
* **DeleteUser**
* **GetUser**
* **UpdateUser**

권한 정책에 접근 권한을 제공하는 조건을 지정할 수 있어 요청이 지정된 조건을 충족할 때 자원을 제공한다. 특정 조건을 지정하려면 정책 문장의 조건 요소를 사용하면 된다. IAM이 요청 내 연산을 승인한 후, 주체는 관련 작업을 수행할 수 있기에 자원들과 리소스들은 서비스 내에 존재하는 객체이다.
